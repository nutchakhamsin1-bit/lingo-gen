# Lingo Gen — แปลเอกสารหลายไฟล์ในพื้นที่ทำงานเดียว

Interactive prototype (Frontend) ของเว็บแอปแปลเอกสารแบบชุด: เพิ่มได้หลายไฟล์ ตั้งค่าภาษา/โทนครั้งเดียว สั่งแปลทั้งชุด
ติดตามสถานะรายไฟล์ ดูผลลัพธ์เทียบต้นฉบับ และดาวน์โหลดรายไฟล์หรือรวมเป็น ZIP

**ไฟล์ที่แปลแล้วเป็นนามสกุลและรูปแบบเดิมเสมอ** — Word ได้ Word, PDF ได้ PDF, รูปได้รูป โดยแทนเฉพาะข้อความ
(สไตล์ ตาราง รูป กราฟ เลย์เอาต์ คงเดิม)

> **โหมดทดลอง** — เปิดไฟล์และสร้างไฟล์ผลลัพธ์จริงบนเครื่อง แต่ข้อความเป็นคำแปลจำลอง `[TH] ข้อความเดิม`
> (ชื่อไฟล์ขึ้นต้นด้วย `DEMO_`) การตรวจจับภาษา/โทนยังไม่ประมวลผลจริง และไม่มีการส่งไฟล์ออกไปภายนอก

## เริ่มใช้งาน

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # tsc -b && vite build  → dist/
npm run preview    # เสิร์ฟ dist/ เพื่อทดสอบ production build
npm run lint       # oxlint
```

Stack: React 19 + TypeScript + Vite 8 + Tailwind CSS 4 + Lucide Icons + JSZip
· pdf.js + pdf-lib (PDF) · Tesseract.js (OCR) · yaml · gifenc · UTIF (TIFF) — ไลบรารีไฟล์โหลดเมื่อใช้งานจริงเท่านั้น

## ประเภทไฟล์ และวิธีคงรูปแบบ

สูงสุด 10 ไฟล์/ชุด · ไม่เกิน 20 MB/ไฟล์ · รายการนามสกุลอยู่ที่ `FILE_KIND` ใน `src/lib/constants.ts`

| ไฟล์ | สิ่งที่แปล | สิ่งที่คงเดิม |
| ---- | ---------- | ------------- |
| DOCX PPTX XLSX | ข้อความในย่อหน้า ตาราง หัว/ท้ายกระดาษ เชิงอรรถ กล่องข้อความ กราฟ SmartArt (Excel: เฉพาะเซลล์ข้อความ) | สไตล์ ตัวหนา/เอียงภายในประโยค รูป ตัวเลข สูตร เลย์เอาต์ |
| ODT ODS ODP | ย่อหน้าและหัวข้อ (รวมในตาราง/กล่องข้อความ/เชิงอรรถ) | สไตล์ span ลิงก์ รูป |
| PDF | ข้อความทุกย่อหน้า (หน้าสแกนใช้ OCR) | หน้ากระดาษ รูป เส้น สีพื้น สีตัวอักษร ตำแหน่ง |
| RTF | ข้อความทุกย่อหน้า | ฟอนต์ สี ตัวหนา/เอียง |
| EPUB | ทุกบท สารบัญ ชื่อหนังสือ | สไตล์ รูป ฟอนต์ โครงสร้างไฟล์ |
| HTML XML | ข้อความที่ผู้อ่านเห็น, alt/title, meta description | แท็ก คลาส สคริปต์ สไตล์ `<pre>` `<code>` ลิงก์ |
| TXT MD | ทีละบรรทัด (MD: เซลล์ตาราง ข้อความลิงก์) | การขึ้นบรรทัด หัวข้อ รายการ โค้ด URL front matter |
| CSV TSV JSON YAML PO | ค่าที่เป็นข้อความสำหรับคนอ่าน (PO: เติม msgstr) | คีย์ ตัวเลข รหัส ลิงก์ ตัวคั่น คอมเมนต์ |
| SRT VTT | ข้อความคำบรรยาย | ลำดับ เวลา แท็ก `<i>` `{\an8}` |
| PNG JPG WEBP GIF BMP TIFF SVG | ข้อความในภาพ (OCR) | ภาพประกอบทั้งหมด — SVG ได้คำแปลเป็นตัวอักษรเวกเตอร์ |
| DOC XLS PPT HEIC | ต้องให้เซิร์ฟเวอร์แปลง (เบราว์เซอร์สร้างไฟล์เหล่านี้ไม่ได้) | — |

ข้อจำกัดที่ควรรู้

- **PDF:** ข้อความเดิมถูกปิดด้วยสีพื้นแล้ววางคำแปลทับ (ยังคัดลอก/ค้นหาข้อความเดิมได้ใต้คำแปล)
  - คงการจัดชิดซ้าย/กึ่งกลาง/ขวา ตัวหนา และสีตัวอักษรเดิม · บรรทัดที่ต้นฉบับตั้งใจขึ้นใหม่ (หัวกระดาษ รายการ ที่อยู่)
    แยกเป็นคนละส่วน ส่วนย่อหน้าที่ตัดบรรทัดเพราะเต็มจะรวมกันก่อนแปล
  - คำแปลที่ยาวกว่าใช้พื้นที่ว่างข้าง ๆ ก่อนจึงลดขนาดตัวอักษร · ข้อความเอียง/แนวตั้งคงเดิม
  - ฟอนต์ (Sarabun / Noto Sans JP SC KR ทั้งตัวปกติและตัวหนา) โหลดจาก CDN jsDelivr ครั้งแรก
    ตัดให้เหลือเฉพาะตัวอักษรที่ใช้ด้วย HarfBuzz (`src/lib/formats/fontSubset.ts`) — ตัวตัดฟอนต์ของ pdf-lib
    ทำตัวอักษรหายกับฟอนต์ CJK · ตัวอักษรที่ฟอนต์ภาษาปลายทางไม่มี (เช่น ชื่อไทยในเอกสารญี่ปุ่น) ใช้ฟอนต์ของระบบอักษรนั้นแทน
  - วาดทีละ glyph ตามตำแหน่งจาก fontkit (drawText ของ pdf-lib ทิ้งตำแหน่งสระ/วรรณยุกต์ไทย)
  - PDF ที่สั่งพิมพ์จาก Chrome เก็บวรรณยุกต์ที่ซ้อนบนสระบนเป็นรหัสว่าง ("ที่" ดึงได้เป็น "ที") —
    `src/lib/formats/pdfToUnicode.ts` เทียบรูปทรง glyph เพื่อเติมรหัสคืนก่อนอ่าน (ตัวที่เทียบไม่ชัดจะไม่เดา)
- **GIF:** บันทึกเฉพาะเฟรมแรก (ภาพเคลื่อนไหวจะหยุดนิ่ง) · **WebP:** ต้องใช้เบราว์เซอร์ที่บันทึก WebP ได้ (Chrome/Edge)
- **ไฟล์ที่ตั้งรหัสผ่าน** เปิดไม่ได้ — ปลดรหัสผ่านก่อน

## กติกาสำคัญของ Prototype

- ตรวจไฟล์ซ้ำ ไฟล์ว่าง ประเภทไม่รองรับ และขนาดเกิน พร้อมเหตุผล
- การตั้งค่าถูก snapshot ไว้กับงานตอนกด "แปลทั้งหมด" — เปลี่ยนค่าภายหลังไม่กระทบไฟล์ที่เสร็จแล้ว
- ไฟล์ตัวอย่าง 4 รายการเป็นไฟล์จริงใน `src/assets/samples` แปลผ่านขั้นตอนเดียวกับไฟล์ของผู้ใช้
  (หน้ามังงะใช้ตำแหน่งช่องคำพูดและคำแปลจริงที่เตรียมไว้ใน `sampleContent.ts`)
- คลังคำศัพท์ถูกแทนลงในคำแปลจำลองจริง (เช่น `Lingo → ลิงโก้`)
- การตั้งค่า คลังคำศัพท์ และประวัติ เก็บใน `localStorage` (`lingo.*.v1`) · ไฟล์ที่แปลแล้วเก็บใน IndexedDB (`lingo`)
- ทดสอบสถานะผิดพลาด: ตั้งชื่อไฟล์ให้มีคำว่า `error` แล้วสั่งแปล

## การทดสอบ

```bash
npm test             # unit test (Vitest + jsdom) — ตัวอ่าน/เขียนไฟล์ทุกนามสกุล ไม่ถึง 2 วินาที
npm run test:e2e     # ทดสอบในแอปจริง (Playwright + Chrome ที่ติดตั้งในเครื่อง) — ประมาณ 1 นาที
```

- **Unit** (`src/**/*.test.ts`): ตัวแปลง segment และตัวจัดการแต่ละนามสกุล — ตรวจว่าโครงสร้างไฟล์ไม่เสีย เช่น
  ตัวหนาย้ายตามลำดับคำแปล, run ของ PowerPoint มี `<a:t>` ตัวเดียว, `mimetype` ของ ODF/EPUB อยู่ไฟล์แรกแบบไม่บีบอัด,
  ค่ารหัส/ตัวเลขใน CSV/JSON/Excel ไม่ถูกแปล
- **E2E** (`e2e/`): อัปโหลด → แปล → ดาวน์โหลด ZIP แล้วตรวจไฟล์ผลลัพธ์จริง ครอบคลุม PDF (กู้วรรณยุกต์ไทยจากไฟล์ที่พิมพ์จาก Chrome
  และคัดลอกข้อความจาก PDF ที่แปลแล้วได้ถูกต้อง), OCR การ์ตูน 3 ช่องคำพูด, ภาพ 6 นามสกุล, ปุ่มหยุด และประวัติหลังรีเฟรช
  - ต้องต่ออินเทอร์เน็ต (ฟอนต์และโมเดล OCR โหลดจาก CDN) · ไฟล์ทดสอบอยู่ที่ `e2e/fixtures/` (ข้อมูลสมมติทั้งหมด)
  - `e2e/fixtures/thai-quotation.pdf` สร้างจาก `e2e/fixtures/source/thai-quotation.html` ด้วย Chrome (คำสั่งอยู่ในไฟล์)
- **CI** (`.github/workflows/ci.yml`): lint → build → unit → e2e ทุกครั้งที่ push ขึ้น `main` หรือเปิด pull request

## เปลี่ยนจาก Mock เป็น API จริง

UI คุยกับ `TranslationService` interface เท่านั้น จึงสลับ provider ได้โดยไม่แก้ UI:

```bash
# .env.local
VITE_TRANSLATION_PROVIDER=http
VITE_TRANSLATION_API_URL=https://your-backend.example.com/api
```

### 1) ไฟล์ที่เบราว์เซอร์สร้างเองได้ (เกือบทุกนามสกุล) — ส่งเฉพาะข้อความ

แอปแยกข้อความ (และ OCR รูปภาพ) บนเครื่อง ส่ง **เฉพาะข้อความ** ไปแปล แล้วสร้างไฟล์นามสกุล/รูปแบบเดิมเอง —
ตัวไฟล์ไม่ถูกส่งออก backend จึงเป็นแค่ตัวแปลข้อความ (DeepL, Google, LLM ฯลฯ)

| Method | Path            | หน้าที่                                                                                  |
| ------ | --------------- | ---------------------------------------------------------------------------------------- |
| POST   | `/jobs`         | JSON `{ fileName, ext, segments: string[], settings, glossary }` → `{ jobId }`           |
| GET    | `/jobs/{jobId}` | `{ status, progress, translations?: string[], error? }` — คำแปลตามลำดับและจำนวนเท่า `segments` |

แต่ละ segment escape แบบ XML และอาจมีแท็ก **ที่ต้องคงไว้ในคำแปล** (ย้ายตำแหน่งได้ตามไวยากรณ์):

```text
Lingo turns a <g1>folder of documents</g1> into a set.<x2/>See <g3>docs</g3>
```

- `<gN>…</gN>` = ช่วงที่มีรูปแบบต่างไป (ตัวหนา ลิงก์) · `<xN/>` = ห้ามแตะ (ขึ้นบรรทัด แท็บ โค้ด รูป)
- DeepL: `tag_handling=xml` · Google: `format=html` · LLM: สั่งให้คงแท็กและ escape เดิม

### 2) DOC XLS PPT HEIC — อัปโหลดไฟล์ให้ backend แปลทั้งไฟล์

| Method | Path            | หน้าที่                                                           |
| ------ | --------------- | ----------------------------------------------------------------- |
| POST   | `/jobs`         | multipart: `file`, `settings` (JSON), `glossary` (JSON) → `{ jobId }` |
| GET    | `/jobs/{jobId}` | `{ status, progress, outputUrl?, error? }` — ลิงก์ไฟล์ที่แปลแล้ว (นามสกุลเดิม) |

### รูปภาพที่มีทั้งภาพและตัวอักษร (มังงะ ป้าย อินโฟกราฟิก)

แปล **เฉพาะข้อความ** แล้ววางคำแปลกลับตำแหน่งเดิม ภาพประกอบไม่ถูกแตะ

- **OCR บนเครื่อง** ด้วย [Tesseract.js](https://github.com/naptha/tesseract.js) (`src/services/ocr/`) — ภาพไม่ถูกส่งออก
  ครั้งแรกจะดาวน์โหลดตัว OCR และโมเดลภาษา (หลาย MB) จาก CDN jsDelivr แล้วแคชไว้ในเบราว์เซอร์
  - หาช่องคำพูดจากภาพก่อนแล้วอ่านทีละช่อง จากนั้นอ่านทั้งภาพเพื่อเก็บข้อความนอกช่อง แล้วจัดกลุ่มคำที่อยู่ใกล้กัน
  - ภาษาที่อ่านตามภาษาต้นฉบับที่ตั้งไว้ (ญี่ปุ่น/จีนรวมโมเดลตัวอักษรแนวตั้ง) · "ตรวจจับอัตโนมัติ" อ่านเป็นภาษาอังกฤษ
- แต่ละจุดเป็น 1 segment — แอปลบข้อความเดิมด้วยสีพื้นรอบกรอบ แล้วจัดขนาด/ตัดบรรทัดคำแปลให้พอดีกรอบ
  (ตัดคำไทย ญี่ปุ่น จีน ด้วย `Intl.Segmenter` และไม่ให้เครื่องหมายวรรคตอนขึ้นต้นบรรทัด)
- ข้อจำกัด: วางคำแปลแนวนอนเท่านั้น · ตัวอักษรบนพื้นลวดลายลบได้ไม่เนียน (ต้องใช้ inpainting)
  · Tesseract ยังพลาดกับฟอนต์ลายมือ ตัวอักษรเอียง หรือเสียงประกอบ (SFX) — งานมังงะญี่ปุ่นจริงจังควรใช้ OCR เฉพาะทาง

**ห้ามใส่ API key ของผู้ให้บริการแปลใน Frontend** — backend เป็นผู้ถือ credential และเป็นผู้เรียกบริการแปลจริง
